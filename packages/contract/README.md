# contract

The Bulb contract: the bulb config JSON Schema, TypeScript types generated from it, and a config loader.

- Schema (source of truth): `src/schemas/bulb-config.schema.json`.
- Types: `src/generated/bulb-config.ts`, generated by `npm run generate`; never edit by hand. A test fails when they
  are stale.

## Loading a config

```ts
import { readBulbConfigFile, parseDurationMs } from '<contract package>';

const config = await readBulbConfigFile('.bulb/config.yaml'); // defaults filled in
parseDurationMs(config.responsibilities['dep-updates']?.min_release_age ?? '0d'); // milliseconds
```

`loadBulbConfig(yamlText)` and `parseBulbConfig(value)` do the same for text and parsed values. Invalid configs throw
`BulbConfigError`, whose `issues` list `{ path, message }` entries such as `budget.per_task_usd: unknown key` or
`notify.on[3]: must be equal to one of the allowed values: ...`. Messages never include config values.

## Type generation and validation errors

`scripts/generate.ts` holds a list of schema entries (`schemaEntries`). To add a schema: add the file under
`src/schemas/`, add an entry to the list, and run `npm run generate`.

The document parsers (`parseWakeEvent` and the others below) throw `ContractValidationError`, which has a `document` name and the same
`{ path, message }` `issues` as `BulbConfigError`. Messages never include input values.

## Wake events, outcomes and lifecycle notifications

Each document has a schema in `src/schemas/`, a generated type and a parser. Parsers take any value, return a
validated clone, and throw `ContractValidationError` (no defaults are filled in).

```ts
import { parseWakeEvent, parseOutcome, parseLifecycleNotification } from '<contract package>';
```

Shared shapes: ids are 1 to 128 characters of `[A-Za-z0-9._:-]` starting with a letter or digit; `repo` is
`owner/name`; `responsibility` is `dep-updates`, `vuln-patch` or `ci-fix` (an outcome's may also be `null`, see
below); `caused_by` is `{ kind: 'event' | 'task', id }`;
`links` is up to 20 `{ kind: 'pr' | 'run' | 'logs' | 'check' | 'other', url }` entries with http(s) URLs.

### Wake event (`WakeEvent`, `parseWakeEvent`, `wakeEventSchema`)

Required: `id`, `source` (`github`, `schedule`, `dashboard` or `bulb`), `type` (dotted, e.g. `dependabot.pr.opened`,
`schedule.tick`), `repo`, `payload` (source-specific object, never secrets) and `depth` (integer, `0` for an external
root event). `caused_by` is optional at depth 0 and required at depth 1 or more. The schema sets no maximum depth; the
runner enforces that.

### Outcome (`Outcome`, `parseOutcome`, `outcomeSchema`)

Required: `task_id`, `responsibility`, `repo`, `outcome` (`done`, `ready`, `blocked`, `error` or `skipped`), `summary`
(one line, up to 200 characters) and `cost` (`{ cad, minutes }`, both >= 0; minutes are runner wall time). Optional:
`tried` (up to 20 entries), `why`, `decision_needed`, `links` and `verification_signal` (`ci_checks`,
`platform_check`, `verify_commands` or `none`).

`blocked` and `error` must carry `decision_needed`; without it the only issue reported is
`decision_needed: is required`. The rule is a root `if`/`then` that Ajv enforces at runtime, so the generated type
keeps `decision_needed?: string`.

`responsibility` is `null` only when the runner ended the event before a responsibility ran (an event type no
configured responsibility handles, or an event past the maximum depth); that is allowed only with `skipped`,
otherwise the issue is `outcome: must be equal to constant`.

### Lifecycle notification (`LifecycleNotification`, `parseLifecycleNotification`, `lifecycleNotificationSchema`)

Sent when a task begins; it is not an outcome and does not end a task. Required: `notification` (only `started`),
`task_id`, `responsibility` and `repo`. Optional: `caused_by`, `summary` and `links`.

## Task state and responsibility scope

```ts
import { parseTaskState, assertTaskStateSize, parseResponsibilityScope } from '<contract package>';
```

### Task state (`TaskState`, `parseTaskState`, `taskStateSchema`)

What a task carries between wake-ups, stored as compact JSON in a hidden PR comment. Required: `version` (must be
`1`), `task_id`, `responsibility`, `attempts` (0 to 100), `cost_so_far_cad` and `minutes_so_far` (both >= 0; minutes
are runner wall time only), `phase` and `caused_by`. Optional: `deadline`, a UTC timestamp as produced by
`Date#toISOString`.

`phase` is `running` (working) or `waiting` (asleep until an event or the deadline) while the task is live, or the
outcome it ended in (`done`, `ready`, `blocked`, `error` or `skipped`). `waiting` requires `deadline`.

Serialised as compact `JSON.stringify` output, task state must be at most `TASK_STATE_MAX_BYTES` (10,240) UTF-8 bytes.
`taskStateByteLength(state)` measures it and `assertTaskStateSize(state)` throws a `RangeError` over the limit (the
message gives only the sizes). The schema has no field for logs, transcripts or free text; such keys are rejected.

### Responsibility scope (`ResponsibilityScope`, `parseResponsibilityScope`, `responsibilityScopeSchema`)

The paths a responsibility may change. Required: `responsibility` and `paths` (1 to 100 unique globs, relative to each
configured directory; no leading `/`, no `..` segment, no backslash, and no brace or extglob syntax `{ } ( )`, so
glob expansion cannot produce a `..` segment). Optional: `max_diff_lines` (integer >= 1). The
runner always excludes `never_touch` and workflow paths, whatever the allowlist says. The real allowlists ship with
each responsibility package.

## Dashboard API

The HTTP API the core uses to save and load task state and to report to the optional dashboard. The core works
without the dashboard; this package is the source of truth for the API, and the dashboard implements it.

```ts
import { dashboardApiPath, matchDashboardApiRoute, parseDashboardError } from '<contract package>';
```

Request bodies are the existing contract documents, unchanged. `dashboardApiEndpoints` lists the endpoints;
`dashboardApiPath(id, { repo, task_id? })` builds a URL-encoded path (and throws `RangeError` for an invalid `repo` or
`task_id`, without echoing it), and `matchDashboardApiRoute(method, pathname)` routes a request.

| Endpoint id | Method | Path | Request body | Success (200) |
| --- | --- | --- | --- | --- |
| `save_task_state` | `PUT` | `/v1/repos/{owner}/{name}/tasks/{task_id}/state` | `TaskState` | `DashboardAck` |
| `load_task_state` | `GET` | `/v1/repos/{owner}/{name}/tasks/{task_id}/state` | none | `TaskState` |
| `post_outcome` | `POST` | `/v1/repos/{owner}/{name}/outcomes` | `Outcome` | `DashboardAck` |
| `post_notification` | `POST` | `/v1/repos/{owner}/{name}/notifications` | `LifecycleNotification` | `DashboardAck` |

Each path segment is URL-encoded. `DashboardAck` is `{ ok: true }` (`parseDashboardAck`, `dashboardAckSchema`).
Loading a task state that was never saved gives 404 `not_found`.

### Auth header (`DashboardRequestHeaders`, `parseDashboardRequestHeaders`, `dashboardRequestHeadersSchema`)

Every request sends `Authorization: Bearer <token>` (`DASHBOARD_AUTH_HEADER`, `DASHBOARD_AUTH_SCHEME`). The scheme is
case-sensitive and the token uses the RFC 6750 characters `[A-Za-z0-9._~+/-]` with optional trailing `=`. The
contract defines only the header's shape, not where the token comes from. The token is a secret: it never appears in
logs, error bodies or recorded requests, and validation issues show the schema pattern, never the value.

### Errors (`DashboardError`, `parseDashboardError`, `dashboardErrorSchema`)

Any endpoint can answer with a status >= 400 and the body `{ error, message, issues? }`. `message` is one line and
never contains request values or credentials; `issues` (up to 50) are the `{ path, message }` issues from the contract
parsers, passed through `toDashboardErrorIssues`. A path can hold a client-supplied key name of any length, so that
helper keeps the first 50 issues and truncates each `path` and `message` to 500 code points; send raw parser issues
and the body may break the schema. `DASHBOARD_ERROR_STATUS` maps each code to its status:

| `error` | Status | When |
| --- | --- | --- |
| `invalid_request` | 400 | the body is not JSON, fails its schema, or its `task_id` (state) or `repo` (outcome, notification) differs from the path |
| `unauthorized` | 401 | the auth header is missing or the token is wrong |
| `not_found` | 404 | unknown path, or no task state saved |
| `method_not_allowed` | 405 | known path, wrong method |
| `payload_too_large` | 413 | the body is too large, or a saved task state is over `TASK_STATE_MAX_BYTES` (10,240 bytes, the same limit as the PR-comment store, so a state can move between stores) |
| `internal` | 500 | anything else |

### Idempotency

Saving task state is a `PUT` and overwrites. A task has exactly one outcome, keyed by (`repo`, `task_id`), so a
retried post replaces the earlier one. A notification is keyed by (`repo`, `task_id`, `notification`). Repeats return
200. Wake events are not part of this API; dashboard dispatch reaches the core through GitHub.

### Mock dashboard server

`startMockDashboardServer` is a local, in-memory implementation of this API for tests of the dashboard adapters. It
is for tests only and lives behind a separate `./testing` subpath so `node:http` stays out of the main entry. From
other workspaces import `<contract package>/testing` after `npm run build` (it resolves to `dist/`); inside this
package use the relative path `src/testing/index.js`.

```ts
const server = await startMockDashboardServer({ token: 'test-token' });
// server.url, e.g. http://127.0.0.1:54321; send `Authorization: Bearer test-token`
await server.close();
```

Options: `token` (required; non-empty RFC 6750 token characters, else `TypeError`), `host` (default `127.0.0.1`) and
`port` (default `0`, any free port). The server validates every request as described above and checks its own
responses against the schemas.

Inspection: `requests` (method, path, endpoint id and status only; never headers or bodies), `taskState(repo, taskId)`,
`outcomes()`, `notifications()` (clones, in insertion order), `seedTaskState(repo, state)`, `reset()` and `close()`.

## Defaults

Omitted keys take the defaults written in each key's schema `description`. Required: `version` (must be `1`) and
`responsibilities` (at least one). A responsibility is configured when its key is present, e.g. `ci-fix: {}`; absent
responsibilities get no default object.

| Key | Default |
| --- | --- |
| `engine.provider` | `"anthropic"` |
| `engine.model` | none (the engine adapter picks one) |
| `engine.effort` | `"medium"` |
| `context.include` | `[]` |
| `verify.commands` | `[]` |
| `verify.working_directory` | `"."` |
| `verify.timeout` | `"2h"` |
| `merge.auto_merge` | `false` |
| `merge.require_verified` | `true` |
| `notify.webhook` | none |
| `notify.on` | `["ready", "blocked", "error"]` |
| `responsibilities.<any>.enabled` | `true` |
| `dep-updates.schedule` | `"weekly"` |
| `dep-updates.directories`, `vuln-patch.directories` | `["."]` |
| `dep-updates.allow` | `["patch", "minor"]` |
| `dep-updates.min_release_age` | `"7d"` |
| `dep-updates.hold` | `{}` |
| `dep-updates.group` | `"weekly"` |
| `ci-fix.attempts` | `2` (1 to 100, matching the task state cap) |
| `ci-fix.max_diff_lines` | `200` |
| `budget.per_task_cad` | `1` |
| `budget.per_task_minutes` | `15` |
| `safety.never_touch` | `[".env*", "**/secrets/**"]` |
| `safety.never_push_default_branch` | `true` |
| `safety.never_force_push` | `true` |
| `safety.workflow_files` | `"blocked"` (the only allowed value) |

`min_release_age` defaults to 7 days, the chosen MVP default; a repo can set its own (Personal-Website uses `14d` in
its config).

`notify.webhook` is kept as an opaque string: the loader does not interpolate `${{ ... }}`; resolving it is the
reporter's job.

`extends` and `uses:` are reserved for inherited defaults and third-party responsibilities later; for now they are
rejected as unknown keys like any other.

## Durations

`verify.timeout` and `min_release_age` are `<integer><unit>` with unit `m`, `h` or `d` (`0d` allowed only for
`min_release_age`).
